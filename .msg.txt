fix(protocol): accept the panel-only declined field on a plan

dream/status adds `declined` to each pending plan so an action the user already
dismissed comes back marked instead of looking like a fresh suggestion. The
parser's key whitelist never learned about it, so the panel failed with
"dream plan has unknown field: declined" — after a run that had finally produced
a real, storable plan.

Effect: the one screen that would have shown the first working proposal could not
render at all.

`declined` is optional: `dream/proposal/read` serves the plan file as stored and
that file carries no such field. It is validated when present (array of
non-empty strings) and unknown keys are still refused, so widening the record
does not open it up.

The plan itself is intact on disk: one set-priority action on
qq-companion-session. Nothing was lost; only the view was blocked.
